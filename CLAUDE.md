# Training: running plan viewer and gym log

A small installable web app (PWA) called **Training** that shows the owner's running plan on their phone: today's and tomorrow's runs in detail (Upcoming), the weeks (Plan), and a short summary, highlights and goals (Guide). An opt-in **Gym** tab (Settings → Gym) logs lifts. The top bar shows the plan doc's title (its first Heading 1). It is hosted on GitHub Pages from this repository (`running-ent/Training`, branch `claude/workout-plan-viewer-m7t1w9`) at **https://running-ent.github.io/Training/**.

**Why a separate GitHub organization:** Chrome on Android lets only one installed web app per site address, and the recipe app already lives on `entquine.github.io`. This app must stay on its own address (`running-ent.github.io`), or one of the two apps can't be installed. Don't move it back under `entquine`. The owner is not a developer: explain things in plain language and don't ask them to run commands. Anything the owner should paste elsewhere (for example a prompt for their other AI) goes in a fenced code block so it has a copy button. It is built like the recipe app in `entquine/recipes`.

## Privacy rule (important)

**This repository is public. Never commit the plan or anything from it**: no copy of the plan (HTML, Markdown, docx, JSON), no workout text, no race names, dates, paces or heart-rate numbers in code, comments, tests, fixtures or commit messages, and **no Google Doc link** (anyone with that link can read the plan). Test files built from the real plan stay outside the repository (for example in a scratch directory).

## Where the plan lives

- **Master copy:** the "Running Plan" doc in Claude (a Claude Docs document, `https://claude.ai/artifact/X4e3PY7mMom94a8aNprpY1`; the doc is private to the owner, so this link alone shows nothing to anyone else). The owner and Claude edit the plan there.
- **What the app reads:** the Firestore document `plan/current` in the Firebase project `traininghoster` (fields `html`, `updatedAt`, `source`). Its rules (kept in the Firebase console only, since they contain email addresses) let **only the owner's login read it** and **only the sync login write it**. Everything else is denied.
- **More than one login:** each login reads its own plan from the Firestore document named after its email (lowercase, every character that isn't a letter or digit turned into `_`); if that document doesn't exist the app falls back to `plan/current` (the first login's plan). Another person's plan is synced with `node tools/sync-plan.mjs <saved result> --to <that name>`. Never put emails (or the names made from them) or the master doc links of other people in this repository.
- The app signs in with email and password through Firebase's REST APIs (no SDK, no build), keeps the sign-in on the phone, and keeps the last plan it loaded so it works with no signal.

## Syncing the plan to the app (the usual task)

When the owner asks to "sync the plan" (or a scheduled task does):

1. Read the Running Plan doc with the Claude Docs connector: `read` the tab's content node (`ref {"object":"node","id":"1967751b-6cad"}`, `container {"kind":"project","id":"f37437f2-d72d-435e-8d17-3aed85d5a51a"}`). If that node id no longer works, `read` the project first to find the tab's content node. The result is large and is saved to a file; note its path.
2. Send it: `node tools/sync-plan.mjs <saved result>`. It converts the read in memory (with `tools/xml_to_html.py`, so no plan file is written), refuses anything with no "Week N" headings, and prints one line (bytes, weeks, time). If the plan is identical to the last one it sent for that person (it keeps a fingerprint in `~/.cache/runplan-sync`, outside the repository), it sends nothing and says "unchanged", so phones don't download it again; `--force` sends anyway. It needs `RUNPLAN_SYNC_EMAIL` and `RUNPLAN_SYNC_PASSWORD` from the environment settings, and network access to `identitytoolkit.googleapis.com` and `firestore.googleapis.com`. (It also accepts an HTML file made with `python3 -I tools/xml_to_html.py <saved result> > <scratch dir>/plan.html`.)
(The app's status pill is hidden while the plan is synced, and the gym log too when the Gym tab is on; it appears only when something has been wrong, such as no signal or an error, for 3 seconds.)
3. Tell the owner it's synced and that the app picks it up within about 2 minutes while open, or as soon as it's opened or brought back on screen (or Settings → Check for updates). Don't print or quote the plan in the output beyond what the owner asked about.

Never commit `plan.html` or the saved read result, and never ask the owner to paste a password into the chat.

## What the app expects in the doc

The app reads the structure, not specific wording:

- **Title**: the first Heading 1 (or a "Title" paragraph). It becomes the app's title.
- **Guide tab**: shows only the Heading 2 sections whose titles start with **Summary**, **Highlights** and **Goals** (in that order). Every other non-week section stays in the doc for Claude's use and isn't shown. Summary gets an "at a glance" strip the app works out (next race and days to go, week of the plan, miles and runs done). Highlights bullets written `Label: text` become cards with an icon picked from the topic. A Goals table with a chance/odds column becomes goal cards with a bar for the chance (the first column is the badge, the next one the big value); text before the table shows, text after it doesn't.
- **Weeks**: a heading `Week N: <dates> (<summary>)`, Heading 2 or 3, followed by a 2-column table whose first row is `Day | Workout`. Each row's day cell must contain a date as `month/day` (e.g. `Mon M/D`). Years are worked out automatically. Paragraphs under the table show below that week. Week headings under a Heading 2 (as Heading 3) are grouped under that Heading 2 on the **Plan** tab.
- **Week recap**: under a week's table, a paragraph `Recap: ...` (first sentence = bold verdict; more sentences, or bullets right after it, become bullets) and `Rating: Great|Good|OK|Tough`. Shown at the top of that week's page; the rating also shows on the week's card on the Plan tab.
- **Estimates** (no doc changes needed): upcoming runs written in miles show an estimated time (each step's `at m:ss` pace, or the typical easy pace; steps with no amount, like a cool-down until HR drops, are named as extra), and runs written in minutes show an estimated distance.
- **Weeks: miles and time** (no doc changes needed): every week's page and Plan card show miles and time together. The week in progress shows done, to go and planned with a bar and an "on track" note; past weeks show done of planned; coming weeks show planned. Time done is each finished run's own time (`in N min` in its `Done:` line, also on split days), else its planned time; planned time comes from the steps (paces, or the typical easy pace). Day mileage estimates are scaled to add up to the week heading's total, so the note only reflects finished runs that came in longer or shorter than planned (or were skipped). A finished run's Time tile also shows its planned time.
- **Charts** (no doc changes needed): *Weekly miles* on the Plan tab (planned = the `N mi` in the week heading, so the heading should keep the planned total, else the days' steps added up, with minutes turned into miles at the typical easy pace; done = distances from `Done:` lines, else the planned distance; weeks with a race day get a small gold flag labeled 5K, 10K, Half, Full or Race, from the race's headline). *Progress* on the Guide tab, between Highlights and Goals (pace and average heart rate of finished easy and long runs; recovery runs and treadmill runs, any day whose plan or `Done:` mentions "treadmill", are left out).
- **A day's Workout cell** is separate paragraphs, each starting with a label and a colon:
  - The first paragraph (no label needed, or `Plan:`) is a **short headline**, e.g. `Hill session, N mi`. Bullets right under it are the **steps**, one per bullet: `N mi easy`, `N x N min hard with N min jog`, `N mi tempo at m:ss`. The app draws a colored bar of the run from them (easy, steady, tempo, hard, recover; paced steps get warmer as the pace gets faster).
  - `Keep in mind:`, `Before:`, `During:`, `After:`: shown for today and future days (Upcoming tab and week view). Bullets under a label belong to it.
  - `Done:` what actually happened. Start with the numbers (`N mi in N min, HR N, m:ss pace`, or splits `m:ss, m:ss, m:ss` plus a total such as `N mi total`): the app shows them as tiles and the rest as bullets. A `Done:` starting with "Skipped", "Missed" or "Rested" marks a planned run as **skipped** (yellow: label, reason box and Plan dot; the card keeps its run-type color). A plan starting with `REST` is a **planned rest** (purple).
  - `Steps:` (finished runs, optional) followed by one bullet per planned step, in the same order, saying what happened (time, pace or distance, and the step's average heart rate as `HR N`). Each finished step shows its average heart rate as a chip (green inside the step's target `HR a to b`, `HR below N` or `HR about N`, amber outside); the result shows under it only when its amount differs from the plan, and tapping the step shows (under the step, above any result line) the low-to-high range during the step, labeled Range, (`HR avg, range low to high` or `HR avg (low-high)` in the log) and the step's target. Upcoming steps show their target as the chip.
  - `Review:` the coach's take on a finished day. The first sentence is shown as a bold verdict, the rest as bullets.
  - `Rating:` optional one word (Great, Good, OK, Tough), shown as a colored badge on the day.
  - `Shoe:` the shoe for that day when it differs from the shoe table (planned swap, or what was actually worn). It replaces the table's shoe for that day.
  - Older one-line cells still work: `Title: a, b, c` is split into steps, and "Done:" mid-sentence starts the Done part.
- **Shoes**: a table whose header row is `Week | Sun | Mon | ...` gives each day's shoe, by week number. A day's own `Shoe:` line wins over it.
- Day type colors come from the plan text: `REST...`, races (race day, half, 5K, 10K, marathon in the first phrase; gold), `Long run`, workouts (ladder, tempo, intervals, fartlek, progression, hills, ...), otherwise easy.

## Gym tab (opt in)

- Off by default; Settings → the "Show the Gym tab" switch (saved on the phone; no heading or note, so Settings fits one screen). Off hides the tab; the log stays.
- The tab opens on a search box ("Find an exercise") and four big buttons that fill the screen, two by two: **Chest day**, **Back day**, **Legs day**, **Other**, each in its own color with a line icon (Chest: bench press, Back: deadlift, Legs: standing with the bar on the shoulders, Other: kettlebell; `GYM_DAY_ICONS`) and the date it was last done (nothing if never). Typing in the search box swaps the four buttons for the matching exercises from every day (with their day's name). The four buttons share the height left on screen (`fitGym`), so the top level never scrolls. **Add exercise** is a button in the header on this page only; it opens a small form (`3x8 Name`, or just a name, and a dropdown for the day, defaulting to Other).
- Each day's page (`#/gym/chest|back|legs|other`, with a Back button) has a big button per exercise, two to a row and three rows to a screen (`fitGym` sizes the rows from the space left, so six exercises and the Doing now bar fit without scrolling; more than six scroll): a line icon of its own (`GYM_ICONS` by name; exercises added in the app get a general one from `gymIcon`), the name, its sets x reps (e.g. 4x5) and the date last done (nothing if never). **Hold one (about half a second) and drag** to reorder the day (no note on the page about it); the order is saved per day (`order` in the log, newest change wins when merging). A quick swipe still scrolls.
- Tapping an exercise opens **its own page** (`#/gym/<day>/<name>`, title = the exercise, nothing else on it), which starts it; leaving is the header's Back or the phone's Back (if the page was opened directly, Back and logging go to its day instead). While it's in progress, other gym pages show a slim "Doing now" bar that opens it, and the Gym tab has a dot. The page fits one screen (notes and past sessions may run below): the weight (pre-filled with last time's, or one step up after "no problem"; for a barbell, "Total **N lb**" under it; and the change from last session, or from the starting weight when there's none, in green "+5 lb" or red "−5 lb" or "no change", counted like the log: the bar's total, one dumbbell, or the machine total); a **Warm-up** checkbox; **Finished sets** with − and + (starts at the planned number of sets from the sets x reps, 3 when there's none; from 0 up to that number); the four results (Couldn't, Almost, Barely, No Problem), which log it and go back; a full-width "Cancel" (leaves without logging); **Notes** for that exercise (a box that saves as you type and shows every time; `notes` in the log, newest edit wins when merging, and follows renames); and "Past sessions (N)" folded at the bottom (shows "3 of 4 sets" when short and "warm-up"; an entry can be deleted). Entries from the version with a button per set show each set's reps ("5 5 5 2"). Weights are in lb.
- **Weight types** (fixed per exercise, not changeable in the app; to change one, edit `gymDefaultWType`): **Barbell**: you enter the weight on each side, steps of 2.5, and the page shows the total (2 x side + 45 lb bar, `GYM_BAR`); **Dumbbells**: the weight of each dumbbell ("lb each"), steps of 2.5; **Machine / total**: the total, steps of 2.5. Defaults (`gymDefaultWType`): Bench Press, Incline Bench, Overhead Press, Squat, Deadlift, Pendlay Row, Hip Thrusts are Barbell; names with dumbbell, curl (not leg curl or a machine), bicep, split squat, lunge are Dumbbells; everything else Machine / total (Curl Machine and Seated Leg Curl included). Renamed exercises are listed in `GYM_ALIASES`, so old entries and order follow the new name. Entries store `weight` (the total for a barbell, one dumbbell for dumbbells), `wtype`, `side`, `done`/`of` (finished/planned sets) and `warmup`; history shows "225 lb (90 a side)", "25 lb each" or "120 lb". After "No Problem" the next session starts one step up: 2.5 lb in the number you enter (a side on a bar, so 5 lb total; each dumbbell; or the machine total). The −/+ buttons also move 2.5.
- The exercise list is `GYM_DEFAULTS` in `app.js` (group, sets x reps, name, optional hidden search words: Overhead Press is found by "OHP"). There's no remove button in the app. Entries logged under a name that's no longer listed still show under Other. Icons follow the recipe app's style: one path, 24 by 24, stroke 2, round ends; most show a person doing the movement (side or front view, with an arrow where it helps). The owner approves new drawings before they go in.
- **Starting weights**: numbers with no date, used only to fill in the weight of an exercise that has no sessions yet (nothing else shows them: no note, no past-session line, no date). They live in the Firestore document `gymstart/<email name>` (field `start`, a JSON list of {ex, wtype, weight, side?}), which only that login can read and only the sync login can write (a rule block per person in the console). Send them with `node tools/gym-start.mjs <JSON file> --to <email name>`; keep the JSON file outside the repository (the numbers are personal, like the plan). The app reads them with the gym backup and keeps a copy on the phone.
- Saved on the phone at once and backed up to the Firestore document `gym/<the login's Firebase user id>` (field `log`, JSON: `custom` [{group, scheme, name}], `removed`, `entries` [{id, ex, scheme, date, at, weight, wtype, side?, done, of, warmup, result}], `deleted`, `order` {day: {names, at}}; the first version's `exercises` list is migrated). Phone and backup merge by entry id. The backup needs this in the Firestore rules (no emails in it):
  `match /gym/{uid} { allow read: if request.auth != null && request.auth.uid == uid; allow write: if request.auth != null && request.auth.uid == uid && request.resource.data.keys().hasOnly(['log', 'updatedAt']) && request.resource.data.log is string && request.resource.data.log.size() < 900000; }`
  Without it the tab still works (the log stays on the phone). Backup trouble shows in the **status pill** at the top, like plan trouble: "Gym log not backed up yet" (a change waiting for signal), "Gym backup failed" (Firebase refused it) or "Gym backup is off" (rules). A waiting change is retried at every check (every 2 minutes while open, when signal returns, on opening the app), and by the pill, pull-down and Check for updates; the pill goes away once it's backed up. There's no backup line on the gym pages.

## Files

- `index.html`, `styles.css`, `app.js`: the app. No build step; edit them directly.
- `sw.js`: service worker for offline use. **Bump `VERSION` in `sw.js` and `APP_VERSION` in `app.js` together** whenever any app file changes, so phones pick up the new version (Settings → Check for updates). After pushing, end the message to the owner with the live version on its own line, e.g. `Version: rN`.
- `manifest.webmanifest`, `icons/`: home-screen install. The manifest's `theme_color` is a neutral near-black (like the recipe app), so the phone's own bars around the installed app stay neutral whatever color is picked; the header's color comes from the page. Android only picks up manifest changes when it refreshes the installed app (can take a day or more) or on a reinstall.
- `tools/xml_to_html.py`, `tools/sync-plan.mjs`: the sync (see above). `tools/gym-start.mjs`: sends starting gym weights (see Gym).
- Preview another date with `?today=YYYY-MM-DD` on the app's address.
- **Pull to refresh**: pulling down from the top of any page (past a threshold; a round arrow shows the pull) runs the same `checkForUpdates` as Settings → Check for updates (plan and app version, same messages). Installed apps don't get the browser's own pull-to-refresh, and `overscroll-behavior-y: contain` keeps the browser's from doubling it in a tab. The recipe app has none.
- **Settings** fits one screen: sign-in line with Sign out, Color, the Gym switch, then the version with Check for updates. Every button and switch sits on the right.
- **Color** (Settings → Color): nine themes like the recipe app (`THEMES` in `app.js`, `:root[data-color=...]` rules at the end of `styles.css`, light and dark), chosen per phone and applied before the page draws by a line in `index.html`. Ocean (the original blue) is the default. The header and the phone's status bar follow it; run-type and chart colors don't change.

## Checking a change

Serve the folder (`python3 -m http.server`) and open it in Playwright, routing `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` and `firestore.googleapis.com` to mocked responses that carry a test plan. Keep that test doc outside the repository (see the privacy rule).
